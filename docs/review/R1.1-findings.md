## F01 — Concurrent exports can erase previously exported lines

- **Severity:** high.
- **File and line:** `src/remy_finance/registry/store.py:423`–`430` (`Registry.export`).
- **What breaks:** The export operation reads existing exported heads and file contents, constructs a replacement, then atomically replaces the file without interprocess exclusion. Exporter A can prepare recommendation sequence 1; exporter B then appends sequence 2 and successfully exports both rows; A resumes and replaces B's longer file with its older one-row version. Publication is atomic, but the day file shrinks and a successfully exported row disappears. This violates the accepted append-only export behavior and weakens the external evidence anchor.
- **Minimal reproduction:** `test_f01_concurrent_export_cannot_erase_already_exported_rows`. At A's replacement boundary, another real registry handle appends a second recommendation and exports it. A then finishes; the final file no longer starts with the successful longer export. The injected boundary forces a valid interleaving; it does not replace the registry's read/write operations.
- **Suggested fix:** Serialize the entire head-discovery/read/append/publication operation with a cross-process export lock. Use one consistent database snapshot for the rows being exported. Coordinate this with scheduler export pushes so local publication cannot race staging/committing.

## F02 — Verification accepts a same-name trigger that no longer enforces immutability

- **Severity:** medium.
- **File and line:** `src/remy_finance/registry/store.py:328`–`334`.
- **What breaks:** `verify()` checks installed trigger names only. Replacing `recommendations_no_update` with a same-name no-op trigger disables the UPDATE protection while verification still reports success. This is a failure to detect tampering with the guard, not a claim that ordinary SQL bypasses an intact original trigger.
- **Minimal reproduction:** `test_f02_verify_detects_replaced_noop_trigger`. Using a separate SQLite connection, replace the trigger with `BEFORE UPDATE ON recommendations BEGIN SELECT 1; END`; demonstrate that an UPDATE succeeds; assert that verification rejects the altered guard. Actual result: `verify().ok` is true.
- **Suggested fix:** Verify trigger target tables and definitions against the expected schema using stable normalization or an equivalent behavioral check. A matching name alone is insufficient.

## F03 — Changes to the SQL journal.kind column are invisible to verification and export

- **Severity:** medium.
- **File and line:** `src/remy_finance/registry/store.py:308`–`313` (`rows`); related checks at `:365`–`411`.
- **What breaks:** `journal.kind` is omitted from `Row`, the verification read, and exported row comparisons. After an event is exported, changing only that physical column leaves `verify(export_dir=...)` successful even when the original trigger definitions have been restored. The canonical event JSON remains unchanged, so normal parsed-event consumers still see its original kind; the defect is undetected column inconsistency and failure of the brief's stored-row tamper invariant.
- **Minimal reproduction:** `test_f03_verify_and_export_detect_changed_journal_kind`. Export an `ORDER_SUBMITTED`, temporarily remove its UPDATE trigger, change the SQL column to `TRADE_CLOSED`, restore the original trigger, then verify against the unchanged export. Expected rejection; actual success.
- **Suggested fix:** Read the SQL kind and compare it with the parsed `JournalEvent.kind`. Include it in external row anchoring if the export is intended to cover all stored columns, or remove the redundant column through a separately versioned schema change.

## F04 — Verification can falsely reject a healthy database during concurrent appends

- **Severity:** medium.
- **File and line:** `src/remy_finance/registry/store.py:339`–`341`.
- **What breaks:** Verification reads recommendations and journal in separate autocommit snapshots. Another handle can append a recommendation and its first event after verification has read recommendations but before it reads journal. Verification then sees the event without its recommendation and reports an unknown trade. CLI export verifies first, so ordinary concurrent activity can refuse a healthy export.
- **Minimal reproduction:** `test_f04_verify_uses_one_snapshot_while_another_writer_appends`. After the real recommendation read, a second handle commits a valid new recommendation and `ORDER_SUBMITTED`; verification subsequently reports `event for unknown trade`.
- **Suggested fix:** Run the complete verification, including export comparisons, inside one explicit consistent read transaction. Do not use incremental caches for integrity verification.
