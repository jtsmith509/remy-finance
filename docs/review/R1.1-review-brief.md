# R1.1 code review brief: the paper-trade registry

**For:** an independent reviewer, such as Codex, who hasn't seen how the code was written.
**Scope:** `src/remy_finance/registry/` and the `remy registry` commands in `src/remy_finance/cli.py`, on branch `claude/cool-pascal-80kptn`.
**Goal:** find defects in the registry **before** the fill engine and baselines start writing to it. Every prospective result depends on this store being append-only and tamper-evident. Style comments are low priority.

## 1. Read first (about 10 minutes)
1. `CLAUDE.md`: the ground rules.
2. `docs/handoff/HANDOFF_R0_R1.md` §6 R1.1, and `docs/spec/spec_v0.5.md` §11 (the required recommendation and outcome fields, and the immutability rule).
3. `docs/decisions/DR-0028-registry-details.md`: the design choices (proposed). DR-0012 and DR-0016 are accepted.

## 2. Run (offline)
```bash
uv sync
uv run ruff check . && uv run ruff format --check . && uv run mypy
uv run pytest -q tests/unit/registry tests/property/test_registry_tamper.py tests/integration/test_cli_registry.py
uv run pytest -q   # everything, about 384 tests
```

## 3. Invariants to attack (most important first)
For each invariant, try to build an input that breaks it. If you can, write a failing test.

1. **Append-only.** No UPDATE or DELETE gets through on `meta`, `recommendations` or `journal` through the public API or through plain SQL while the triggers are in place.
   - Think about `INSERT OR REPLACE`, `REPLACE INTO`, `UPSERT`, `ON CONFLICT`, foreign-key cascades, `VACUUM`, and `ALTER TABLE`.
   - `INSERT OR REPLACE` was found to bypass the DELETE triggers during development. It is now blocked by the `*_next_row_only` insert triggers (DR-0028 §10). Please try to get round that guard.
   - Can a row be overwritten without firing a DELETE trigger?
2. **Tamper evidence.** `Registry.verify` must report any change to a stored row: its content, its hashes, the sequence, the chain links, the mode, or the triggers.
   - Known limit (DR-0028 §8): a truncated tail is caught only against an export. Is anything else undetectable without the export?
   - Does `_check_export` compare the right things? Could an exported file be edited to hide a truncation?
3. **Chain-head races.** `add_recommendation` and `add_event` read the head and insert inside `BEGIN IMMEDIATE`. Can two processes, such as the scheduler and a manual run, both write seq N+1, or fork the chain?
4. **Mode separation.** A replay record must never reach the prospective database, and the reverse.
   - Check `registry_path`, the `meta` stamp, `Registry.open(mode=None)`, the CLI `--mode` handling, and the export subfolders.
5. **Record validation** (`registry/records.py`).
   - Can a `Recommendation` exist whose capital at risk, $ return, expiration, fill rule, exit policy or trade ID disagree with its candidate?
   - Can a null move or a zero-quantity trade be recommended?
   - Are the Decimal and float rules (DR-0025) respected: no float anywhere, exact products?
6. **Lifecycle** (`registry/lifecycle.py`).
   - Is any impossible history accepted? Is any legitimate one refused, for example: assignment then forced exit; an exit that is unfilled several times then settled at expiration; a 4-leg entry written as 4 `LEG_FILLED` events?
   - Does a failed append ever leave a partial row?
7. **Export.**
   - Is `registry export` incremental and idempotent across days?
   - Can a crash mid-export lose or duplicate lines?
   - Is the export file's earlier content ever rewritten differently?

## 4. Already settled (don't re-report unless you find a defect in the implementation)
- **Storage:** SQLite and WAL (D12, accepted).
- **Chain layout:** per-table chains (DR-0028 §1, proposed: comments welcome).
- **Null decisions:** not stored in the recommendations table (DR-0028 §11).
- **Out of scope:** pushing the export to the `registry-export` branch is R1.6 work.

## 5. How to report
Use one entry per finding, with these fields:
- **ID:** F01, F02, …
- **Severity:** critical, high, medium or low.
- **File and line.**
- **What breaks.**
- **A minimal reproduction:** ideally a failing pytest.
- **Suggested fix.**

Findings and their resolutions will be recorded in `docs/review/R1.1-findings.md`, with a regression test for each fix.
